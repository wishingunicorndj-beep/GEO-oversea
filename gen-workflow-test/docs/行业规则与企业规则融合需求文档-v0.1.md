# GEO 行业规范与企业规则融合需求文档

版本：v0.1  
状态：第一版需求草案  
项目：`gen-workflow-test`

## 一、建设目标

在现有“客户资料 → 企业规则 → Dify 工作流 → 文章评估”的基础上，增加行业内容质量能力。

```text
行业资料 + 销售场景 + 客户资料
        ↓
行业规范 + 企业规则
        ↓
本次文章质量标准
        ↓
Dify 生文工作流 + 批次评估
```

系统最终需要分别判断：

- 是否符合客户规则；
- 是否符合行业底线；
- 是否达到行业专业质量；
- 关键主张是否有证据；
- 是否帮助目标用户做出判断。

## 二、第一版范围

### 2.1 纳入范围

1. 销售填写行业内容场景表；
2. 销售上传客户写作要求和相关资料；
3. 系统选择一套已经审核通过的行业规范；
4. 模型从客户资料中提取企业规则；
5. 模型根据行业规范、企业规则和本次场景生成文章质量标准；
6. 将有效规则注入现有 YAML 母版；
7. 导出客户版 Dify 生文工作流；
8. 使用同一份有效标准评估生成文章；
9. 保存行业规范、企业规则和文章质量标准的版本快照。

### 2.2 第一版暂不做

- 自动生成法律结论；
- 每次销售提需求时重新生成正式行业规范；
- 一次覆盖完整的医疗、教育或金融行业；
- 替代法务、行业专家或客户最终审核；
- 改变现有 Dify 节点拓扑；
- 自动抓取全部行业资料。

## 三、核心概念

### 3.1 行业规范

行业规范是可以被多个客户复用的行业内容质量标准，来源包括：

- 法律法规和监管文件；
- 行业标准和专业指南；
- 专家意见和专业共识；
- 处罚、投诉、纠纷和整改案例；
- 用户高频问题和常见误解；
- 高质量内容样本。

行业规范规定：

- 哪些主张存在风险；
- 用户必须理解哪些概念、条件和边界；
- 哪些内容需要证据；
- 什么样的文章才算专业、完整、可信。

行业规范需要独立建设、审核、版本化和复用。销售提需求时只能选择已经生效的行业规范，不能直接修改行业规范。

### 3.2 企业规则

企业规则来自单个客户的资料，规定：

- 品牌和产品如何称呼；
- 客户希望重点表达什么；
- 哪些词和内容不能出现；
- 企业业务边界是什么；
- 哪些事实和数据已经被客户确认。

企业规则只属于当前客户，不能被直接提升为行业标准。

### 3.3 文章质量标准

文章质量标准是针对本次文章任务最终生效的标准：

```text
文章质量标准
= 当前场景适用的行业规范
+ 当前客户适用的企业规则
+ 本次文章任务要求
```

它同时用于大纲规划、生文、内容审核和批次评估。

## 四、第一版试点场景

第一版先验证一个具体场景：

```text
行业：教育培训
受众：小学阶段家长
文章目的：帮助家长比较和选择课程
文章类型：课程介绍 / 课程选择指南
决策阶段：比较和报名之前
```

这只是验证流程，不代表第一版要覆盖完整教育行业。

## 五、角色职责

### 5.1 销售

销售负责提供真实业务场景和用户问题，不负责定义行业规范。

销售提供：

- 行业和细分行业；
- 目标受众；
- 文章目的和类型；
- 用户问题；
- 客户希望重点表达的内容；
- 已知审核风险；
- 客户提供的资料。

### 5.2 行业规范负责人

负责：

- 收集行业依据；
- 组织模型提炼行业规范；
- 判断规范是否适用于指定场景；
- 处理规则冲突和不确定内容；
- 发布正式行业规范版本。

### 5.3 客户

负责确认：

- 企业规则是否提取准确；
- 企业事实是否真实；
- 品牌和业务边界是否正确；
- 本次文章质量标准是否符合业务目标。

### 5.4 行业专家或法务

针对医疗、教育、金融等高风险领域，复核：

- 行业底线；
- 证据要求；
- 风险提示；
- 适用条件和例外情况。

## 六、销售需求表

销售需求表填写的是“本次文章场景”，不是行业规范本身。

### 6.1 基础字段

| 字段 | 是否必填 | 说明 |
|---|---:|---|
| 客户名称 | 是 | 关联客户项目 |
| 客户标识 | 是 | 对应现有 `slug` |
| 行业 | 是 | 医疗、教育、金融等 |
| 细分行业 | 是 | 例如小学素质教育、人身保险 |
| 文章主题 | 是 | 本次文章主题或关键词方向 |
| 文章类型 | 是 | 科普、介绍、比较、案例、选择指南等 |
| 内容目的 | 是 | 认知、比较、选择、转化、风险教育等 |
| 目标受众 | 是 | 主要读者及其角色 |
| 决策阶段 | 是 | 了解、比较、核实、选择、使用后评估等 |

### 6.2 七项场景内容

1. **适用场景**：行业、受众、文章目的、文章类型、决策阶段。
2. **用户决策**：用户需要判断什么，最容易做出什么错误判断。
3. **专业判断维度**：专业人士通常会看哪些因素。
4. **必须解释**：用户必须理解哪些概念、条件、边界和区别。
5. **必须避免**：哪些高风险表达、过强结论和误导方式需要避免。
6. **证据要求**：哪些主张需要数据、资质、案例或其他来源。
7. **质量目标**：希望文章达到怎样的完整性、专业性、可信度和决策价值。

这七项只是场景输入。没有行业依据和审核，它们不能自动成为正式行业规范。

## 七、客户资料上传

支持上传：

- 客户写作规范；
- 历史文章修改意见；
- 客户审核反馈；
- 品牌和产品资料；
- 企业事实和服务资料；
- 客户确认的禁用和指定表达；
- 数据、案例、资质和官方证明材料。

模型必须区分：

```text
写作要求 → 企业规则
企业事实 → 客户知识资料
行业观点 → 没有外部依据时不能认定为行业规范
```

## 八、行业规范来源

正式行业规范应基于：

- 法律法规和监管文件；
- 国家标准、行业标准和专业指南；
- 行业协会规范和专家共识；
- 处罚、投诉、纠纷和整改案例；
- 用户问题和常见错误认知；
- 高质量文章样本。

如果当前场景没有已审核的行业规范：

1. 系统提示当前没有可用行业规范；
2. 允许创建行业规范草案；
3. 草案必须经过人工或专家审核；
4. 未审核的草案不能直接用于正式工作流。

## 九、模型处理流程

### 9.1 提取企业规则

输入：客户资料。

输出：沿用现有 `rules.yaml` 分类的企业规则草案：

- `identity`：实体和品牌称谓；
- `fact`：企业事实口径；
- `prohibition`：禁止表达和禁止内容；
- `stance`：企业定位和比较边界；
- `scope`：业务关联边界；
- `voice`：口吻和体裁；
- `structure`：文章结构要求；
- `citation`：数据和引用要求；
- `delivery`：人工确认等流程要求。

### 9.2 激活行业规范

模型根据以下内容，从正式行业规范中筛选本次适用部分：

- 行业和细分行业；
- 目标受众；
- 内容目的；
- 文章类型；
- 决策阶段；
- 文章主题。

原行业规范不能被本次任务修改。

### 9.3 生成文章质量标准

模型输入：

```text
正式行业规范
+ 销售需求表
+ 企业规则草案
+ 客户证据资料
```

模型输出：

```yaml
quality_standard:
  scenario: 本次文章场景
  audience: 目标受众
  purpose: 内容目的
  must_explain: 必须解释的内容
  must_prove: 必须证明的主张和证据要求
  must_avoid: 必须避免的主张和误导方式
  outline_requirements: 大纲必须覆盖的内容
  generation_requirements: 正文表达要求
  evaluation_requirements: 成文后的评估要求
  human_review_items: 必须人工审核的内容
  source_trace: 每项要求的来源
  conflicts: 尚未解决的冲突
```

模型不得：

- 把客户偏好直接变成行业底线；
- 没有依据时补充法律结论；
- 把销售经验直接升级为专业标准；
- 忽略规则的适用条件和例外；
- 静默裁决行业规则和企业规则的冲突。

## 十、规则融合原则

```text
行业规范：专业和风险底线
企业规则：客户个性化表达和业务边界
文章质量标准：本篇文章最终怎么写、怎么验收
```

默认优先级：

```text
强制性行业底线 > 企业一般表达偏好
```

发生冲突时必须展示：

- 冲突双方；
- 各自来源；
- 适用条件；
- 建议处理方式；
- 是否需要人工确认。

## 十一、母版 YAML 对接

第一版保留现有工作流拓扑，新增三个上下文槽位：

```text
industry_standard
enterprise_rules
article_quality_standard
```

| 内容 | 主要使用位置 |
|---|---|
| 行业专业判断 | 场景分析、大纲规划 |
| 行业底线 | 大纲、生文、内容审核 |
| 企业品牌和业务规则 | 场景分析、大纲、生文、内容审核 |
| 文章质量标准 | 大纲、生文、内容审核、评估 |
| 禁词、替换、正则 | N8-pre 确定性门禁 |
| 评估要求 | 项目评估器和批次报告 |

完整法规原文不直接注入每个节点，工作流只接收筛选、结构化、场景化后的有效标准。

## 十二、批次评估

报告至少区分：

```text
企业规则符合度
行业底线通过情况
行业专业质量
证据完整度
用户决策价值
人工审核项
```

每项行业要求需要保留：

- 规则 ID；
- 来源；
- 适用场景；
- 判定结果；
- 原文证据；
- 修改建议；
- 判定方式：代码、模型或人工。

现有 `rules_snapshot.yaml` 需要增加来源记录：

```yaml
resolved_from:
  industry_standard:
    id: education-course-choice
    version: 0.1.0
  enterprise_rules:
    client_id: example
    version: 0.1.0
  article_quality_standard:
    version: 0.1.0
```

## 十三、前台流程

```text
销售填写需求表
    ↓
上传客户资料
    ↓
选择行业规范
    ↓
模型提取企业规则
    ↓
模型生成文章质量标准
    ↓
人工确认规则和冲突
    ↓
注入 YAML 母版
    ↓
导出客户版 Dify 工作流
```

## 十四、验收标准

使用一个真实客户和一个真实行业场景完成闭环，并满足：

- 行业规范、企业规则、文章质量标准边界清晰；
- 行业规范可以复用于多个客户；
- 企业规则不会修改行业规范；
- 文章质量标准能够指导大纲和正文生成；
- 现有工作流拓扑保持有效；
- 行业结果和企业结果可以分别统计；
- 证据不足可以标记为无法判定或人工审核；
- 批次可以追溯当时使用的全部版本。

至少测试四类问题：

1. 客户品牌或业务表达错误；
2. 行业底线违规；
3. 行业必要内容缺失；
4. 关键主张缺少证据。

## 十五、实施顺序

1. 选择一个行业、一个受众和一个文章目的；
2. 准备一版经过审核的行业规范；
3. 提取一个真实客户的企业规则；
4. 生成本次文章质量标准；
5. 改造母版 YAML，使其接收三个上下文槽位；
6. 生成并运行一版客户工作流；
7. 导入文章并验证分层评估；
8. 闭环稳定后再建设前台页面。

第一阶段完成标志：

```text
行业资料
→ 行业规范
→ 企业规则
→ 文章质量标准
→ YAML 工作流
→ 文章评估
→ 反馈和版本迭代
```
