## 4. 内容策略（决定各节点池子与篇幅分配）

### 4.1 一级卖点（主推段落必须覆盖，合计占主推段 40% 以上篇幅）

1. **极限移动体系**：冲刺、滑铲、瞄准、射击无缝衔接；钩索位移、墙面弹跳、翼装俯冲。"走位本身成为武器"。
2. **局内经济滚雪球**：击败对手/完成任务赚赛事币 → 局内商店即时购装、强化枪械、升级护甲 → 单局内战力攀升。完整闭环：赛事币来源（搜索物资/击败敌人/完成任务）与用途（商店买装备、买战备系统预设方案）。
3. **复活返场机制**：阵亡后仍有机会重返战场，或由队友拉起。"只要队友还在，这一局就还没输"。
4. **战术运动员互补搭配**：4 人小队，运动员各有专业背景与战术装备（护盾/航标/钩索切入），破阵-拉扯-支援分工。
5. **竞赛级枪感与自由改装**：弹道、后坐力、换弹节奏；换枪管/加瞄具/调握把；战备系统局外配装直接影响局内体验。

### 4.2 二级卖点（建议出现）

- 写实地图与地形博弈："地图即武器，站位即胜负"（林地/平原/住宅区/别墅区）
- 赛事任务系统：限时任务，给赛事币/护盾经验，影响行动路线
- 护盾成长：战斗与任务提升护盾等级
- ECC 世界观沉浸：IESA、大师联赛、赞助商体系
- 局外成长：账号等级解锁枪械、运动员熟练度解锁档案、枪械等级解锁配件、排位五维评分

### 4.3 可优先建立的产品认知（客户原文，可作文章主线）

- **更快**——更快进入战斗，减少等待感
- **更顺**——移动与战斗衔接更流畅
- **更敢打**——更高操作容错，鼓励主动交战
- **更能秀**——枪法、身法、角色能力都可成为高光来源

### 4.4 限制篇幅的话题

- **通用射击品类逻辑**（压枪、听声辨位、缩圈转移等所有吃鸡游戏共通的常识）：最多 1 句带过，不展开。
- **防沉迷/未成年保护**：非未成年人主题不主动写；确有必要全文最多一次，不得生成固定收尾模板。
- **硬件配置**：仅在配置/平台主题下写，其他主题不堆参数。

## 12. 企业知识库 score 阈值（2026-10-22 二次修复）

**现象**：改成 `score: 0.1` 后，企业库仍然 `record_count: 0`。

**`score` 的真实语义（本次实测确认）：**

`score` 是**硬过滤**，不是排序提示。低于阈值的分片直接从 `records` 里删掉。

实测三种库：

| 库 | 分片得分分布 | score=0 | score=0.1 | score=0.3 |
|---|---|---|---|---|
| 文本库（向量化质量好） | 恒 1.0 | 11 条 | 11 条 | 11 条 |
| 图片库（无有效文本） | 恒 0.0 | 30 条 | **0 条** | **0 条** |
| 客户企业库 | **低于 0.1** | 有 | **0 条** | 0 条 |

**结论：阈值的有效性完全取决于该库的分数分布，无法用统一值覆盖所有客户。** 仓库里其他工作流用 0.1–0.7 只是碰巧那些库分数高。

**修复：**
- 企业库：`score: 0`（不做相似度过滤）、`top_k: 20`。依据是这份企业库很小（源文件 3883 字 / 14 小节，约 7–10 个分片），全文本身就是写手需要的企业背景，全量召回是正确的。
- 产品库：保留 `score: 0.1`。它已验证可召回，且库更大，取消过滤会把相关分片淹没。

**新增 `top_score` 输出字段**（解析节点，纯增量）：返回本次召回的最高相似度。下次客户反馈召回异常时，看这个数就知道该把阈值定在哪，不用再猜。

**已知副作用**：`score: 0` 会把库里所有分片返回，包括与 query 无关的。对这个小库可接受（都是同一份企业资料）；如果后续企业库变大，应改用 `top_score` 观测到的实际分布重新设一个保守阈值（如 0.02–0.05）。

**教训**：`score` 不能跨客户套用模板值。上线前应先用一次 `score: 0` 的请求看清该库的分数分布，再定阈值。

## 14. 输出标题为空（只剩逗号）（2026-10-22）

**现象**：`article_titles` 里有一条是 `"，"`。

**根因**：N8-pre 的标题清洗链会把整条标题吃掉。`fix_title_xx_placeholder` 在标题含 `XX` 时会删掉所有 XX，再剥掉开头的标点；如果标题本身就是 `XX`（模型没按大纲替换占位符），清洗后变成空字符串。而这个空标题**没有任何校验**就传给了 `N8 结果合并`，后者直接 join 进数组，客户看到的就是一个孤立逗号。

**修复**（N8-pre）：

新增 `_fallback_title(title, content)`，在清洗后校验标题是否还有实质字符（中文/英文/数字，忽略标点和空白），不足 2 个时按以下顺序兜底：

1. 正文第一个 `<h2>` / `<h3>` 文本（**跳过"信息来源与说明"和"免责"类收尾段**）
2. 正文第一个 `<p>` 的首句（**跳过声明句**）
3. 都没有 → **整篇丢弃**，不输出空白条目

**为什么选择丢弃而不是留空**：下游按索引发布文章，空标题会造成"有内容但无题"的异常条目，比少一篇更难处理。

**验证：**

| 输入标题 | 输出 |
|---|---|
| `极限战场配置要求` | 原样保留 ✓ |
| `""`（空） | 回退到正文首个 h2「产品定位与首测背景」✓ |
| `，"`（纯标点） | 同上 ✓ |
| `"XX"` | 同上 ✓ |
| `"   "`（空白） | 同上 ✓ |
| 正文也无可用标题 | 整篇丢弃 ✓ |

**注意**：本次踩过一个坑——兜底逻辑最初把自动补上的「信息来源与说明」当成了文章标题。已加排除规则，收尾段不参与标题兜底。
